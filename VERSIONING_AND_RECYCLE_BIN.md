# Версионирование и корзина — этап 6

## Требования

Этап 6 устанавливается поверх этапа 5. Перед установкой необходимо сделать резервную копию PostgreSQL и каталога `/upload/sitebuilder`.

Миграция:

```text
/local/sitebuilder/migrations/20260729_002_site_menu_layout_versions_and_recycle_bin.sql
```

Запуск из браузера администратором Битрикс:

```text
/local/sitebuilder/tools/apply_stage6_migration.php
```

Миграция добавляет `version` в таблицы `sitebuilder.site`, `sitebuilder.menu` и `sitebuilder.layout`, расширяет общую историю сущностями `site`, `menu`, `layout` и создаёт `sitebuilder.recycle_bin`.

## Optimistic locking

Изменение существующей сущности требует `expectedVersion`. SQL-обновление выполняется только при совпадении версии, после чего `version` увеличивается на единицу.

При конфликте API возвращает HTTP 409:

```json
{
  "ok": false,
  "error": "VERSION_CONFLICT",
  "entityType": "menu",
  "entityId": 12,
  "expectedVersion": 4,
  "currentVersion": 5
}
```

Версионируемые сущности:

- сайт;
- страница;
- блок страницы;
- меню;
- layout.

## История

API:

- `history.list`;
- `history.get`;
- `history.restore`.

Страница истории сайта, меню или layout:

```text
/local/sitebuilder/versions.php?siteId=13&entityType=site&entityId=13
```

Восстановление старого снимка не удаляет новые ревизии. Снимок записывается как очередная версия с операцией `restore`.

История страниц и блоков остаётся доступна в редакторе.

## Корзина страниц

При `page.delete` в одной транзакции сохраняется снимок всей удаляемой ветки:

- страницы и их иерархия;
- блоки;
- JSON-секции;
- точечные права страниц и Диска;
- удалённые ссылки меню;
- признак главной страницы.

API:

- `trash.list`;
- `trash.get`;
- `trash.restore`;
- `trash.purge`.

Интерфейс:

```text
/local/sitebuilder/trash.php?siteId=13
```

При восстановлении:

1. Проверяется, что старые ID страниц и блоков не заняты.
2. Родительские страницы создаются раньше дочерних.
3. При конфликте slug добавляется суффикс `-restored-<id>`.
4. ID секций сохраняются, а при конфликте безопасно переназначаются.
5. Ссылки блоков на секции обновляются по карте ID.
6. Точечные права возвращаются только при отсутствии записи с тем же `access_code`; более новые ручные настройки не перезаписываются. Ссылки меню добавляются к текущему меню без удаления более новых пунктов.
7. Если восстановленная корневая страница была главной, она снова становится главной только когда у сайта сейчас нет главной страницы.

`trash.purge` окончательно удаляет снимок. После этого восстановление невозможно.

## Права

История и корзина доступны:

- администратору Битрикс;
- `OWNER` и `ADMIN` соответствующего сайта.

`EDITOR`, `VIEWER` и гостевой технический пользователь с ролью `VIEWER` не могут просматривать или восстанавливать корзину.

## Проверка после установки

1. Открыть настройки сайта в двух вкладках.
2. Сохранить изменение в первой вкладке.
3. Попытаться сохранить устаревшую форму во второй — ожидается `VERSION_CONFLICT`.
4. Проверить историю сайта, меню и layout.
5. Удалить страницу с дочерней страницей, блоками, секциями и точечными правами.
6. Проверить состав снимка в корзине.
7. Восстановить ветку и проверить иерархию, блоки, секции, права и меню.
8. Проверить окончательное удаление снимка.

## Ограничения

- Корзина восстанавливает страницы и связанные данные, но не восстанавливает удалённые физические файлы Битрикс.Диска.
- Если старый ID страницы или блока уже занят новой сущностью, восстановление останавливается с `RECYCLE_ENTITY_ID_CONFLICT`, ничего частично не фиксируется.
- JSON-секции хранятся вне PostgreSQL. Для них используется файловая блокировка и компенсирующая очистка при откате операции.


## Секции страниц после этапа 7

Секции хранятся в PostgreSQL, имеют поле `version` и проверяют `expectedVersion`. Снимок корзины по-прежнему включает секции, но их удаление и восстановление теперь атомарны относительно страниц и блоков.
