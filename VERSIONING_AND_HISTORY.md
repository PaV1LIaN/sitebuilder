# Версии страниц и блоков

Этап 5 добавляет optimistic locking и журнал изменений для таблиц:

- `sitebuilder.page`;
- `sitebuilder.block`.

## Перед обновлением

1. Сделайте резервную копию PostgreSQL.
2. Разверните файлы проекта.
3. Примените миграцию `migrations/20260729_001_entity_versions.sql`.
4. Очистите OPcache, если он включён.
5. Только после миграции открывайте редактор SiteBuilder.

Миграцию можно применить одним из способов:

```bash
psql -d DATABASE_NAME -f /path/to/sitebuilder/migrations/20260729_001_entity_versions.sql
```

или открыть от имени администратора Битрикс:

```text
/local/sitebuilder/tools/apply_stage5_migration.php
```

Страница миграции доступна только администратору Битрикс и принимает изменение только POST-запросом с `sessid`.

## Что меняется в базе

В `sitebuilder.page` и `sitebuilder.block` появляется поле:

```sql
version INTEGER NOT NULL DEFAULT 1
```

Создаётся таблица:

```text
sitebuilder.entity_revision
```

Она хранит снимок объекта после каждого изменения. Для существующих страниц и блоков миграция создаёт исходную ревизию с операцией `seed`.

Миграция идемпотентна: её повторный запуск не должен повторно создавать исходные ревизии уже зарегистрированных объектов.

## Контракт optimistic locking

При изменении существующей страницы или блока клиент обязан передавать версию, которую он получил при последнем чтении:

```text
expectedVersion=7
```

Для операций над несколькими объектами передаётся JSON-карта:

```json
{
  "31": 7,
  "32": 4
}
```

в поле:

```text
expectedVersions
```

Если объект уже изменён, API отвечает HTTP 409:

```json
{
  "ok": false,
  "error": "VERSION_CONFLICT",
  "entityType": "page",
  "entityId": 31,
  "expectedVersion": 7,
  "currentVersion": 8
}
```

В этом случае клиент не должен автоматически повторять старое сохранение. Редактор SiteBuilder предупреждает пользователя и перечитывает страницы и блоки с сервера.

## Операции с обязательной версией

Одна версия:

- `page.save`;
- `page.updateMeta`;
- `page.setParent`;
- `page.setStatus`;
- `block.update`;
- `block.delete`;
- `pageSection.assignBlock`;
- `history.restore`.

Карта версий:

- `page.move`;
- `page.delete` — версии всей удаляемой ветки;
- `block.move`;
- `block.reorder` — версии изменяемых блоков.

## Журнал изменений

Добавлены API-действия:

```text
history.list
history.get
history.restore
```

История доступна только пользователю, который имеет право редактировать соответствующую страницу. Для блока проверяется право редактирования страницы, которой он принадлежит.

Основные операции журнала:

- `seed` — состояние на момент миграции;
- `create` — создание;
- `write` — изменение через совместимый внутренний writer;
- `save` — сохранение страницы;
- `meta_update` — изменение свойств страницы;
- `parent_change` — изменение родителя;
- `status_change` — публикация или снятие с публикации;
- `content_update` — изменение блока;
- `placement_change` — изменение секции или колонки блока;
- `reorder` — изменение порядка;
- `restore` — восстановление ревизии;
- `delete` — снимок перед удалением.

Восстановление не затирает историю: оно создаёт новую версию с операцией `restore` и ссылкой `restored_from_revision_id`.

При создании новых страниц и блоков генератор ID учитывает историю удалённых объектов. Пока история существует, ID удалённой сущности повторно не используется и не смешивается с историей нового объекта.

## Состояние после этапа 6

Этот документ описывает базовую миграцию этапа 5 для страниц и блоков. Начиная с этапа 6:

- сайт, меню и layout также имеют собственные версии и историю;
- удалённая ветка страниц восстанавливается из корзины вместе с блоками, секциями, точечными правами и ссылками меню;
- строгие writer-функции используются только при создании и не могут обойти optimistic locking;
- реальные файлы Битрикс.Диска по-прежнему не копируются в ревизии или корзину.

Актуальное продолжение находится в `VERSIONING_AND_RECYCLE_BIN.md`.

## Проверка конфликта

1. Откройте одну страницу редактора в двух браузерах или вкладках.
2. В обеих вкладках выберите одну страницу или один блок.
3. Сохраните изменение в первой вкладке.
4. Попробуйте сохранить старое состояние во второй.
5. Второй запрос должен получить HTTP 409 `VERSION_CONFLICT`.
6. После обновления данных второе сохранение можно выполнить уже на актуальной версии.

## Проверка истории

1. Измените название страницы и сохраните.
2. Откройте «История страницы».
3. Убедитесь, что появилась новая версия.
4. Выберите предыдущую ревизию и нажмите «Восстановить».
5. Убедитесь, что версия увеличилась, а в журнале появилась операция `restore`.
