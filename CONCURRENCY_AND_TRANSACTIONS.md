# Транзакции и конкурентное редактирование SiteBuilder

## Модель этапа 8

Изменяющие запросы `/local/sitebuilder/api/` выполняются в управляемой транзакции PostgreSQL. Общая блокировка всего SiteBuilder удалена. Перед обработчиком `RequestLockService` строит детерминированный план transaction-level advisory locks только для затрагиваемых ресурсов.

Благодаря этому одновременно могут выполняться, например:

- изменения разных сайтов;
- изменения разных блоков одной страницы;
- изменение блока и настроек сайта;
- изменение страниц разных сайтов;
- чтение списков, истории, корзины и журнала.

Операции, меняющие общий порядок, получают более широкий lock:

- сортировка блоков — коллекция блоков страницы;
- изменение дерева страниц — дерево страниц сайта;
- изменение страницы, блока или секции — shared lifecycle-lock страницы;
- дублирование страницы — exclusive lifecycle-lock только исходной страницы;
- изменение меню — конкретное меню;
- изменение layout — layout конкретного сайта;
- удаление ветки или восстановление корзины — exclusive lifecycle-lock сайта.

Полное удаление сайта использует собственную транзакцию и exclusive lifecycle-lock. Обычные изменения этого сайта держат shared lifecycle-lock, поэтому удаление ждёт их завершения, но не блокирует другие сайты.

`maintenance.run` также не оборачивается во внешнюю request-транзакцию: `MaintenanceService` фиксирует очистку до освобождения своей session advisory lock.

## Порядок захвата

Все lock-ключи нормализуются, удаляются дубликаты и сортируются по паре:

```text
namespace → resourceId
```

Exclusive-lock сильнее shared-lock. Одинаковый порядок уменьшает вероятность взаимной блокировки при операциях, затрагивающих несколько объектов.

Если PostgreSQL всё же обнаруживает deadlock или ошибку сериализации, API возвращает:

```json
{
  "ok": false,
  "error": "RETRY_TRANSACTION"
}
```

с HTTP-статусом `409`.

## Ограничение ожидания

В `config/locking.php` задаётся максимальное ожидание resource lock:

```php
<?php
return [
    'lock_timeout_ms' => 10000,
];
```

Допустимый диапазон в коде: от 500 до 60 000 мс. После таймаута транзакция откатывается, а API возвращает HTTP `423`:

```json
{
  "ok": false,
  "error": "RESOURCE_BUSY",
  "resource": "page.blocks",
  "resourceId": 31
}
```

Клиенту следует повторить действие после перечитывания актуального состояния.

## Границы транзакции

Успешный ответ через `sb_json_ok()`:

1. кодируется в JSON;
2. выполняется `COMMIT`;
3. запускаются действия `after commit`;
4. ответ отправляется клиенту.

Ответ с ошибкой через `sb_json_error()` выполняет `ROLLBACK`. Необработанные исключения журналируются, клиент получает стабильный код без SQL, пути к файлам и stack trace.

Автоматическая maintenance запускается только после регистрации общего обработчика исключений.

## Внешние ресурсы

PostgreSQL не может атомарно откатить Битрикс.Диск, файловую систему и социальные группы. Для них используются компенсирующие действия:

- новый логотип или фон удаляется при откате;
- старый файл оформления удаляется только после `COMMIT`;
- загруженный файл Диска удаляется при откате API-запроса;
- созданная рабочая группа Битрикс удаляется при откате создания сайта;
- внешние объекты шаблона очищаются при неуспешном создании сайта.

Просмотр файлов больше не вызывает скрытое создание папки Диска. `file.list` только читает уже привязанную папку. Первичное создание папки выполняется при загрузке файла под lock конкретного сайта.

При аварийном завершении PHP-процесса между внешней операцией и регистрацией компенсации всё ещё может потребоваться административная очистка.

## Optimistic locking

Advisory locks защищают короткую серверную операцию, но не заменяют версию объекта. Сайты, страницы, блоки, меню, layout и секции используют числовой `version`.

Клиент передаёт `expectedVersion`. SQL меняет запись только при совпадении версии. При устаревших данных возвращается:

```json
{
  "ok": false,
  "error": "VERSION_CONFLICT"
}
```

с HTTP `409`. Таким образом:

- resource lock предотвращает одновременное выполнение несовместимых серверных операций;
- optimistic locking обнаруживает, что пользователь редактировал устаревшую форму.

## JSON-хранилища

`templates.json` использует отдельный lock-файл и атомарную замену через временный файл. Секции страниц начиная с этапа 7 находятся в PostgreSQL и участвуют в общей транзакции.

## Проверка после развёртывания

1. Одновременно сохранить два разных блока одной страницы — оба изменения должны сохраниться.
2. Дублировать страницу во время изменения её блока — одна операция должна дождаться другой, а копия получить целостный снимок.
3. Одновременно изменить блок и оформление того же сайта — операции не должны ждать друг друга без необходимости.
4. Одновременно менять порядок блоков одной страницы — запросы должны выполняться последовательно, а устаревший клиент получить конфликт версии.
5. Запустить изменения на двух разных сайтах — один сайт не должен блокировать другой.
6. Начать сохранение страницы и одновременно удалить сайт — удаление должно дождаться сохранения либо вернуть `RESOURCE_BUSY`, без частично удалённых данных.
7. Удерживать lock дольше `lock_timeout_ms` — второй запрос должен получить HTTP `423`.
8. Вызвать первое чтение layout на сайте без layout — должна безопасно создаться одна запись.
9. Открыть пустой Диск гостем — просмотр не должен изменять версию сайта и создавать папку.
10. Одновременно загрузить два файла в ещё не инициализированный Диск сайта — должна появиться одна папка сайта.

Дополнительная карта блокировок описана в `FINE_GRAINED_LOCKING.md`.
