# Права сайтов и папок компонента «Диск»

Автоматическая синхронизация этих ACL с правами SiteBuilder и рабочей группой
портала описана в `UNIFIED_ACCESS_RECONCILIATION.md`.

## Права отдельных сайтов

Права сайта хранятся в `sitebuilder.access` с ключом `site_id`. Один пользователь
может иметь разные роли на разных сайтах:

- `VIEWER` — просмотр страниц и скачивание файлов;
- `EDITOR` — работа с файлами Диска;
- `ADMIN` — управление содержимым и настройками сайта;
- `OWNER` — полный контроль, включая управление правами.

## Права отдельных папок SiteBuilder

Stage 21 добавляет таблицу `sitebuilder.disk_folder_access`. Правило привязано к
конкретному блоку Диска, папке Bitrix Disk и пользователю.

Доступные правила:

- `DENY` — папка и её содержимое недоступны;
- `VIEWER` — просмотр и скачивание;
- `EDITOR` — просмотр и изменение содержимого.

Правило наследуется дочерними папками. Правило, заданное ближе к текущей папке,
имеет приоритет. Удаление правила возвращает наследование от родителя; если
разрешающего правила нет, доступ закрыт. Папочное правило не заменяет допуск
к Диску на этой странице.

Администратор Bitrix, `OWNER` и `ADMIN` сайта не ограничиваются папочными
правилами при работе с файлами.

Кнопки **«Права папки»** и **«Настройки»**, их окна и API доступны только
администраторам Битрикса (`CUser::IsAdmin()`). Роль `OWNER`/`ADMIN` сайта или
список администраторов SiteBuilder не даёт доступа к этим окнам. Восстановить
папочные права через компонент может администратор Битрикса.

## Включение

1. Применить миграцию через `/local/sitebuilder/deployment.php`, CLI
   `tools/migrate_cli.php --apply` или страницу
   `/local/sitebuilder/tools/apply_stage21_migration.php`.
2. В настройках блока «Диск» → «Доступ» включить «Проверять права на папки».
   Автоматически выбирается режим «Индивидуальные права папок SiteBuilder».
3. Открыть нужную папку и нажать «Права папки».
4. Найти пользователя и выбрать правило.

Если выбран режим «Наследовать права сайта», сохранённые папочные правила не
применяются, но остаются в базе и начнут действовать после повторного включения
индивидуального режима.

### Флаг `requireFolderAccess`

Флаг хранится в настройках конкретного блока; он также доступен в редакторе страницы.

| Значение | Поведение |
|---|---|
| `0` / `false` | Режим `inherit_site`: вся структура доступна пользователям с допуском к Диску на этой странице. Возможности изменения и скачивания по-прежнему ограничены ролью и настройками блока. |
| `1` / `true` | Папочные права обязательны: собственное или наследуемое разрешение открывает папку, `DENY` или отсутствие разрешения закрывает её. Общего допуска к Диску недостаточно. |

Без правила на корне пользователь может открыть только его каталог разрешённых
папок. Файлы корня, загрузка в корень и сведения о его заполнении недоступны.
Чтобы предоставить файлы корня, назначьте право на корень: оно наследуется
всеми подпапками, кроме тех, где есть собственное ограничение. Для выборочного
доступа назначайте права нужным папкам. Разрешённую вложенную папку внутри
скрытого родителя можно открыть по прямой ссылке или найти поиском; имена
закрытых родителей не передаются в навигации компонента.

Проверки выполняются на сервере при выводе списка, поиске, открытии и скачивании
файлов. Операция над целой папкой отклоняется, если затрагивает закрытую подпапку.
Выключение флага сохраняет правила в базе для повторного включения.

Флаг согласован с выбором режима: выключение выбирает `inherit_site`, включение
из него — `custom`; выбор `bitrix_disk` включает флаг и использует штатный ACL
вместо правил SiteBuilder. Сам переключатель не переписывает права в портале.
Ссылки и доступ вне SiteBuilder по-прежнему определяются Битрикс24.

Для новых блоков флаг выключен. При обновлении существующие режимы `custom`
и `bitrix_disk` считаются включёнными, чтобы не отключить уже действующие запреты.
**В старом режиме `custom` папки без собственного или наследуемого разрешения
теперь закрыты**, вместо прежнего возврата к правам страницы. Перед обновлением
проверьте назначения. Клиент, не передающий флаг при сохранении настроек Диска,
не сбрасывает его. Новой миграции БД нет.

Проверки флага: `php tests/disk_folder_policy_test.php`,
`node tests/disk_folder_policy_ui_test.js`. GitHub Actions также запускает
проверки массовых прав, ссылок папок, квоты, названий и интерфейса на 1440/768/390 px.

## Массовое назначение правил папки в SiteBuilder

Откройте нужную папку → **Права папки** → **Добавить пользователей списком**.
Вставьте до 200 ФИО, логинов или ID: по одному на строку (подходит столбец Excel).
Нажмите **Найти пользователей**. Поиск не создаёт учётные записи и не меняет права.

Точное единственное совпадение выбирается автоматически. При совпадении ФИО
или неполном имени выберите конкретный логин/ID. Ненайденные и неактивные
пользователи не добавляются. Повторы выбранного ID объединяются.

Выберите «Просмотр», «Редактирование», «Нет доступа» или «Наследовать» и нажмите
**Применить выбранным (N)**. Изменятся только личные правила выбранных пользователей
в текущем блоке и папке. Остальные правила сохранятся. «Наследовать» удаляет личное
правило; действуют правила родителей, а без них доступ закрыт. Собственные правила дочерних папок
не перезаписываются. Для доступа по-прежнему нужны права на страницу и Диск.
Исключения для администраторов/владельцев не меняются.

Запись разрешена только в режиме **Индивидуальные права папок SiteBuilder**.
В других режимах окно предлагает перейти к настройкам; API также отклоняет
сохранение, чтобы не создавать неработающие запреты. Штатный ACL Битрикс этим
окном не меняется.

Пакет сохраняется одной транзакцией PostgreSQL. При ошибке весь пакет откатывается.
Индивидуальные и массовые изменения используют общую транзакционную блокировку
папки. Ревизия защищает массовую запись от затёртых изменений другой вкладки:
при конфликте нажмите **Перечитать права**, проверьте список и повторите применение.

Новой миграции нет: используется существующая таблица этапа 21.

Проверки: `php tests/disk_folder_bulk_test.php`,
`node tests/disk_folder_bulk_ui_test.js`, `npm run test:styles`,
`npm run test:styles:browser`. Тесты используют данные-заглушки Bitrix и не заменяют
проверку под обычной учётной записью на портале.

## Точные права Битрикс24.Диск

Режим `bitrix_disk` использует штатный ACL модуля «Диск» и не записывает
правила в `sitebuilder.disk_folder_access`. В настройках блока выводится матрица
всех активных пользователей, которые могут открыть текущую страницу. Для
каждого пользователя показываются прямое и итоговое право с учётом наследования
папок и групп Битрикс24.

Доступные значения:

| Значение | Задача ACL | Возможности |
|---|---|---|
| Наследовать | прямое правило удаляется | действует ACL родительской папки и групп |
| Нет доступа | отрицательное правило полного доступа | все операции запрещены |
| Чтение | `disk_access_read` | просмотр и скачивание |
| Добавление | `disk_access_add` | чтение, загрузка и создание папок |
| Редактирование | `disk_access_edit` | изменение содержимого без управления правами |
| Полный доступ | `disk_access_full` | полный контроль папки |

Числовые `TASK_ID` не фиксируются в коде: они определяются во время выполнения
через `RightsManager::getTaskIdByName()`. Операции компонента проверяются через
`Bitrix\Disk\Security\DiskSecurityContext`; переключатели блока остаются
дополнительным верхним ограничением.

Положительные права записываются через штатную модель `Bitrix\Disk\Sharing`.
Поэтому пользователь появляется в окне «Поделиться» корпоративного портала, а
ACL содержит домен `SHARING_<id>`, связанный с этой записью. Ранее созданные
SiteBuilder права без sharing-domain заменяются при следующем сохранении
матрицы. «Наследовать» и «Нет доступа» удаляют запись общего доступа.

Матрица изменяет ACL корневой папки выбранного блока. Если блок использует общую
папку сайта, изменения затронут все блоки с тем же `folderId`. Для независимых
прав следует создать отдельную папку блока. Администратор Битрикс24 сохраняет
системный полный доступ, поэтому его строка недоступна для изменения.

### Включение точного режима

1. В настройках блока выбрать «Точные права Битрикс24.Диск» и сохранить общие
   настройки.
2. На вкладке «Доступ» назначить прямое право каждому пользователю страницы.
3. Нажать «Сохранить права».

Миграция базы данных для этого режима не требуется. Запись защищена ревизией ACL
и блокировкой папки; при параллельном изменении матрица будет перечитана перед
повторным сохранением.
