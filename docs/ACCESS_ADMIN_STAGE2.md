# Встроенное управление доступом — этап 2

Продолжение PR #19. Разработка ведётся без установки на рабочий портал. Этап 1 предварительно устанавливать не требуется: итоговый пакет может включать оба этапа.

## Что добавлено

В `/local/sitebuilder/access.php` доступны персональные и массовые назначения штатного Битрикс.Диска (`bitrix_disk`): наследование, нет доступа, чтение, добавление, редактирование, полный доступ. Список по-прежнему принимает до 5000 строк, запись идёт пакетами по 100. Тип прав автоматически определяется по настройкам блока, режим сам не переключается. `inherit_site` изменяется через сайт или Диск страницы; `custom` остаётся локальным ACL.

Изменять штатные права из общей админки может только администратор Битрикс. Администратор Sitebuilder видит их, но не получает административную роль портала. Уровни штатных прав получают ID из работающей установки. Существующие нестандартные/смешанные/частично отрицательные правила отображаются как «Нестандартное правило», а не упрощаются молча.

Пакет затрагивает только выбранных пользователей. Группы, неизвестные уровни и прочие назначения сохраняются; снятие прямого правила не отменяет наследование. Изменение штатных прав физической папки действует во всех её использованиях, в том числе вне Sitebuilder. Наличие сотрудника в таблице не означает, что показаны все члены всех групп: сотрудника с групповым доступом можно добавить поиском для проверки итоговых прав.

## Запрет страницы

Новая **дополняющая** миграция `migrations/20261014_011_page_access_deny.sql` (этап 22) добавляет `sitebuilder.page_access.deny_view BOOLEAN NOT NULL DEFAULT FALSE`. Она зарегистрирована в `MigrationService` и выполняется через существующую страницу развёртывания. Старые SQL-файлы и их контрольные суммы не изменены. Без миграции прежние операции работают, а новый запрет недоступен.

«Нет доступа» закрывает страницу и её Диск для обычного сотрудника, даже если сайт разрешён. Проверка добавлена в общий PageAccessService и фильтр API списка страниц; файловые действия используют общий запрет страницы через свои существующие проверки Диска. Глобальные администраторы, администраторы/владельцы сайта сохраняют доступ.

При включённых «Дочерних» запрет наследуется. Ближайшее явное правило страницы определяет ограничение: отдельное разрешение дочерней страницы может создать исключение. Пустая старая запись и разрешение только Диска не снимают запрет страницы. Старые положительные права остаются добавляющими к роли сайта: «Чтение» не понижает глобального редактора. Существующее отдельное право Диска при запрете сохраняется в БД, но не действует, пока страница запрещена.

Старый редактор флажков не управляет новым запретом. Изменение старых флажков не должно незаметно снимать `deny_view`; снимать явный запрет нужно в новой админке. Удаление прямого назначения восстанавливает правила наследования.

## Запись, ошибки и повтор

Для выбранной физической папки используется PostgreSQL advisory lock, общий для нового и старого редакторов Sitebuilder. Он действует между файловыми серверами кластера при общем подключении к одной PostgreSQL. Посторонние механизмы записи Битрикса эту блокировку не используют: контроль версии и проверка итогового снимка не заменяют координацию с внешними записывающими заданиями.

Штатные права меняются в транзакции Битрикса: пакетное удаление выбранных прямых назначений и пакетное добавление новых, затем проверка результата. Отсутствие транзакционного API не маскируется небезопасным резервным режимом.

БД Sitebuilder и транзакция Битрикса не объявляются одной распределённой транзакцией. До изменения Диска в существующем `audit_log` фиксируется журнал `accessAdmin.native` со снимками «до/после», выбранными сотрудниками и ID запроса. После изменения сохраняется подтверждение. Повтор с тем же ID:

- возвращает готовое подтверждение;
- завершает журнал без повторной выдачи, когда результат уже записан;
- повторяет запись, когда сохранилось исходное состояние;
- останавливается с `NATIVE_RECONCILIATION_REQUIRED`, когда состояние отличается от обоих снимков.

При ошибке нативного пакета выводятся этап операции, папка, затронутые ID/ФИО и группы Битрикса; ошибка всей операции не приписывается вымышленному виновнику. Сбой подтверждения COMMIT не называется гарантированным откатом. Ранее подтверждённые пакеты не отменяются ошибкой следующего.

## Проверки

Локально: PHP lint, Node syntax, прежние изолированные проверки скачивания/удаления и администраторов; новые тесты политики запрета и нативного пакета; два Chromium-теста с подменённым API, включая 500 сотрудников, нестандартные правила и повтор после ошибки.

`tests/access_admin_pg_test.php` проверяет реальные SQL-записи, миграцию, наследуемые запреты и обход для администраторов. `tests/access_native_journal_pg_test.php` проверяет реальный PostgreSQL-журнал и блокировки при тестовой замене Битрикса: сбой append, потерю подтверждения native COMMIT, сбой завершения журнала, конфликт внешнего состояния и неактивного сотрудника после фактически успешной записи.

PostgreSQL-тесты разрешены **только** в отдельной БД `sitebuilder_access_test` с `SB_ACCESS_TEST_ALLOW_RESET=1`; они удаляют тестовую схему. Никогда не запускать их на рабочей базе. Подмена Битрикса в тестах не является проверкой живой коробки. Перед рабочим переходом необходимы проверки обычным сотрудником: список/прямая ссылка, предпросмотр/скачивание, загрузка/удаление/перемещение, наследование и общая физическая папка.

## Совместимость и откат

`config/auth.php`, `config/auth.local.php`, ID администраторов и технического гостя не изменяются. Автоматического отключения/удаления `corp.access` нет. Перед рабочим переходом следует отдельно остановить его записывающие задания и сверить существующие права; во время разработки это не выполняется.

**После начала использования явных запретов нельзя просто вернуть старый код, который не знает `deny_view`: он будет игнорировать запреты.** Для безопасного отката нужно сохранить новую проверку либо предварительно перенести ограничения в эквивалентные поддерживаемые правила. Удаление столбца или данных не входит в откат. Откат файлов не отменяет уже записанные локальные или штатные права Диска; резервная копия и восстановление назначений рассматриваются отдельно.
