# Точечное исправление удаления в Диске — 13.10.2026

## Установка без замены конфигурации

На портале заменяется **только один рабочий файл**:

`/local/sitebuilder/components/disk/actions/delete.php`

Перед заменой сохраните его текущую копию локально. Не загружайте весь архив
репозитория ради этого исправления. Не меняйте `config/auth.php`,
`config/auth.local.php`, `lib/auth.php`, `lib/access.php`, `components/disk/bootstrap.php`
или файлы расчёта прав. SQL-миграций нет. Не запускайте переустановку,
очистку базы или принудительную синхронизацию прав.

Для кластера примените один и тот же файл на всех веб-узлах, если каталог
не общий. При включённом OPcache без проверки времени изменения файла
потребуется принятая на вашем сервере процедура обновления кеша PHP.

Откат: вернуть сохранённую копию **этого же файла**, без восстановления всей базы.
Первоначальная ошибка удаления при таком откате может вернуться.

## Изменения

Удаление больше не использует метод адаптера, который игнорировал результат
`markDeleted()`. HTTP-обработчик вызывает штатное перемещение в корзину,
проверяет boolean-результат и сохраняет ошибки модели Битрикс. Прямого SQL,
безвозвратного удаления или переключения на администратора нет.

Настройки блока читаются без `ensureExistsForBlock()` и без записи
нормализованных свойств — запрос удаления не должен конфликтовать
с параллельным редактированием настроек.

Для всего набора сначала проверяются контекст, принадлежность корню и
существующее право `canDelete` родительской папки. Перед обработкой каждого
объекта проверка повторяется, чтобы обнаружить перемещение/отзыв прав
между элементами пакета. Это не делает внешние действия Битрикс атомарными.
Уже удалённые объекты и дубликаты не обрабатываются повторно.

При ошибке возвращаются ID пользователя, ID проблемного файла/папки,
этап, диагностический код, завершённые элементы и необходимость обновить
список. Исключение после фактического перемещения в корзину не скрывается
и не запускает автоматическое повторное удаление. В таком случае отдельно
указывается наблюдаемое состояние объекта.

В PHP error_log ищите `SiteBuilder Disk delete` и код `SD-...` из ответа.
Запись содержит исходное исключение, стек, ФИО, ID групп Битрикс и
**итоговые права родительской папки**, а не полный разбор каждого правила группы.
Администратор портала также видит техническую причину в сообщении и детали
в JSON. Обычному пользователю SQL, внутренние пути, ФИО и группы не выдаются.
Вывод от сторонних обработчиков и некорректные байты не должны ломать JSON.

## Проверка на портале

1. Убедиться, что Диск открывается у администратора и обычного пользователя.
2. Загрузить ненужный тестовый файл, удалить его под пользователем с правом
   удаления, проверить обновлённый список и корзину.
3. Проверить удаление двух тестовых файлов и отказ у пользователя без прав.
4. При сбое сохранить полный ответ запроса `api.php?action=delete` либо
   текст ошибки администратора с диагностическим кодом. При частичном
   выполнении обновить список перед следующим действием.

## Границы проверки

`php tests/disk_delete_action_test.php` выполняет рабочий обработчик и
настоящий `DiskValidator`, заменяя границы Битрикс/хранилища тестовыми моделями.
Проверяются успех, native false, исключения, частичное удаление, отказы
авторизации/CSRF/прав/контекста, изменившееся расположение, дубликаты,
повторное удаление, изоляция диагностики и корректность JSON.
CI дополнительно запускает существующие тесты локальной авторизации и поиска.

Текст первоначального `SERVER_ERROR` не содержит исходного исключения
с рабочего портала. Подтверждены и исправлены дефекты обработчика, но
наличие отдельной ошибки в модуле Битрикс, его обработчиках событий или
данных сервера исключить без проверки на портале нельзя. Новая диагностика
предназначена для точного определения такой причины, а не для её сокрытия.
