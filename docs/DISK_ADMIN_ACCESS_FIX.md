# Восстановление доступа администратора SiteBuilder к Диску

## Причина

В режиме `permissionMode=bitrix_disk` метод
`DiskPermissionService::resolve()` сначала определял `bitrix_admin` или
`site_admin` с полными правами, но затем **безусловно заменял** их
результатом `BitrixDiskRightsService::resolvePermissions()`.
Встроенный ACL физической папки мог возвратить `canView=false`, включая
администратора портала. Интерфейс показывал «Нет доступа к этой папке».

Исправление сохраняет привилегии двух **действительно административных**
ролей во всех трёх режимах прав: `inherit_site`, `custom` и `bitrix_disk`.

Обычные пользователи в режиме `bitrix_disk` по-прежнему проходят проверку
штатным `DiskSecurityContext` Битрикс. Явные запреты **не снимаются**.
Доступ к папкам за пределами корневой папки сайта также не открывается.

## Безопасное обновление

1. Сохраните копию текущего серверного файла
   `/local/sitebuilder/components/disk/lib/DiskPermissionService.php`.
2. Из обновлённого Git `main` замените **только этот файл** на портале.
   Ни каталог проекта, ни настройки сервера удалять или перезаписывать не нужно.
3. На кластере убедитесь, что этот файл обновился на каждом веб-узле, если
   файлы приложения не находятся на общей файловой системе.
4. При включенном OPcache убедитесь, что новая версия PHP-файла действительно
   загружена. После этого перезагрузите страницу.
5. Проверьте просмотр папки администратором Битрикс и пользователем из
   `config/auth.local.php:admin_user_ids`, затем обычным пользователем
   с явным разрешением, а также пользователем с явным запретом.

**Миграций нет.** Таблицы прав, `auth.php`, `auth.local.php`,
`bootstrap.php`, операции записи файлов и ACL не изменяются.

## Если доступ не появился

В браузере под администратором Битрикс:

1. F12 → Network («Сеть»).
2. Перезагрузите страницу, найдите запрос
   `/local/sitebuilder/components/disk/api.php?action=bootstrap`.
3. Откройте **Response** и проверьте:
   - `ok` — запрос отработал или завершился ошибкой;
   - `data.settings.permissionMode` — `inherit_site`, `custom`
     или `bitrix_disk`;
   - `data.permissions.role` — `bitrix_admin` для администратора
     портала; `site_admin` для администратора SiteBuilder;
   - `data.permissions.canView` — должно быть `true` у администраторов;
   - `data.permissions.accessSource` — источник права.
4. Если `ok=false`, сохраните **код и сообщение ошибки** и проверьте
   PHP error log за это же время. Если `ok=true`, но
   `data.permissions.canView=false` у администратора Битрикс,
   проверьте его фактическое членство в административной группе портала,
   установленную версию файла, OPcache и корректность ID пользователя.
5. Если `bootstrap` вообще не вызывается или приходит HTML, проблема
   в загрузке компонента/авторизации, а не в расчёте `canView`.

Пришлите JSON-ответ `bootstrap` **без токенов сессии и cookies**.
Этого обычно достаточно, чтобы точно определить следующую точку сбоя.

## Важное для обычных пользователей

В режиме `bitrix_disk` права SiteBuilder **не заменяют** права физической
папки Диска Битрикс. Если `data.permissions.accessSource` равно
`bitrix_disk_acl` и `canView=false`, необходимо проверить назначение
прав конкретной папки, её наследование и синхронизацию. Не следует
снимать запреты или переключать режим прав всем пользователям без
проверки того, что это не откроет чужие файлы.

Локальный `config/auth.local.php` с `admin_user_ids` необходимо
хранить отдельно от GitHub и сохранять при каждом обновлении.
