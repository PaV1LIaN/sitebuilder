# Единое управление доступом — этап 4

## Вход и единая модель

Основная страница: `/local/sitebuilder/access.php`.

- **Объекты**: дерево сайтов, страниц, Дисков и папок; прямые групповые назначения, наследование и проход к разрешённой подпапке; создание/изменение назначения группы на выбранном объекте.
- **Группы** (`?view=groups`): прежние создание, массовое добавление, состав, правила и история внутри общей навигации. Новые участники получают те же сохранённые правила; вторых копий назначений нет.
- **Сотрудники** (`?view=employees`): поиск Bitrix-пользователя, участие в локальных группах, включение/исключение из группы и проверка разрешений на выбранном объекте. Перед включением показывается число назначений группы и ссылка на них. Исключение снимает членство во всей группе, на всех её объектах.

`groups.php` остаётся локальным переходом в `access.php?view=groups`. Ссылки с `groupId`, `ruleId` и контекстом объекта открывают нужную группу и правило. Участники в группе ведут в карточку сотрудника; источник разрешения ведёт к правилу, а не к произвольному списку.

## Переход на выдачу через группы, НЕ массовая миграция прав

Основной интерфейс не создаёт персональных назначений. Он изменяет только существующие `access_group*` через `AccessGroupService`, с версиями, аудитом и повтором запроса по тому же requestId. Сохранение из объекта и из группы использует один сервис и одну запись правила.

**Существующие личные разрешения, DENY и резервные права рабочей группы Битрикса продолжают действовать.** В объектах есть разворачиваемая таблица старых прямых назначений; в карточке сотрудника — его сохранённые личные назначения на сайтах/страницах/локальных папках. Это не полный перечень всех штатных разрешений Битрикс.Диска: их проверяют на конкретном объекте.

`access_legacy.php` — явно обозначенный переходный редактор для обслуживания прежних исключений. Старый endpoint `apply`, встроенные старые редакторы и задачи этим обновлением НЕ блокируются. Полный режим «только группы» для выбранного сайта следует включать отдельным этапом, после сверки результата до/после и переноса ограничений. Никаких скрытых групп «один пользователь = одна группа», удаления строк, обнуления ACL или отключения запретов здесь нет.

## Расчёт и объяснение

`AccessGroupPolicy::matching()` — общий отбор применимых правил и для авторизации, и для объяснения групповых источников. Проверяются сайт, страница, текущая физическая иерархия папок, корень блока и режим Диска. Проход к подпапке не называется чтением файлов родителя.

Итог конкретной страницы берётся из `PageAccessService`, папки — из `DiskPermissionService::resolve()`. Последний собирает необязательное объяснение в ходе **того же расчёта**, только по запросу защищённой админки; обычный результат API Диска не расширяется служебной трассировкой. Отдельно видны загрузка, создание папок, переименование, изменение, удаление и скачивание. Наличие источника не гарантирует разрешение: рядом показываются персональные запреты, ограничения блока и штатного Диска.

Групповые источники указаны по конкретному ruleId для конкретного действия, а не по всем группам сотрудника. Старые разрешения страницы и её предков показаны отдельно. Для native ACL показывается результат штатного механизма Битрикса и факт ограничения; полный разбор всех нативных групп и записей ACL не реализован. Статус уровня сайта — сводка назначений на сайт; исключения проверяются на странице или папке.

Отдельные read-endpoint `console.object`, `console.employee`, `console.explain` требуют административных полномочий, POST и CSRF, не записывают данные. Неполный набор более 5 000 групповых правил сайта не выдаётся за полный: возвращается `CONSOLE_RULE_LIMIT`. Таблицы показаны постранично по 100 записей. Это проверка выбранного объекта, не обход всех физических папок портала.

## Установка на тест

Нужен ранее установленный этап групп №25 (PR #22, базовый коммит `4c9afe496edeb8368deca6b5cfff5fa1b8890e85`). **Новых миграций нет.** Базовые файлы SQL и их checksum не изменены.

1. Сохранить папку тестового Sitebuilder и схему БД.
2. Загрузить инкрементальный пакет поверх `/local/sitebuilder/`; не удалять каталог.
3. Открыть `access.php`, при необходимости обновить страницу с очисткой браузерного кэша.
4. На тестовой папке изменить правило существующей группы в разделе «Объекты», открыть эту группу и проверить те же флажки.
5. В разделе «Сотрудники» проверить источники просмотра/изменения/удаления. Исключить тестового сотрудника из одной группы и проверить пересчитанный результат, сохранив доступ от остальных источников.
6. Проверить персональный запрет и неизменность старых личных назначений, права владельцев/администраторов, native ACL при наличии такого режима.

Не запускать worker или старую синхронизацию. Не копировать всю сборку main поверх рабочей версии: ранее найденное расхождение универсальных списков здесь не исправляется. Обновление не меняет auth.php/auth.local.php, подключение БД, маршруты и штатные ACL. Старые отдельные редакторы внутри конструктора и Диска ещё требуют перенаправления/закрытия в этапе окончательного перевода на группы.

Откат этих файлов возвращает прежний интерфейс групп, но не отменяет сделанные пользователем изменения состава и правил. Для отката назначений нужны журнал и резервная копия; не удаляйте таблицы.

## Проверки

- `tests/access_console_policy_test.php`: 2 850 сравнений старой и новой групповой политики на детерминированных наборах правил. Эталон — точная прежняя реализация в тестовом fixture.
- `tests/access_groups_pg_test.php`: реальные PostgreSQL-записи групп/участников/правил, источник каждого действия, отсутствие посторонних групп в объяснении, персональный и native запреты, отсутствие записи при чтении. Bitrix заменён двойниками.
- `tests/access_console_browser_test.py`: реальные PHP-шаблоны, JS и Chromium, но mock API. Проверяет одну запись между представлениями, deep links, отзыв/возврат членства, конфликт версии, replay после потерянного ответа, отсутствие персональных API-записей, XSS, мобильную ширину. В локальной среде URL-навигация браузера заблокирована; смена страниц моделируется загрузкой тех же шаблонов с параметрами ссылки, history заменён тестовым двойником.
- Прежние браузерные тесты персонального редактора перенаправлены на `access_legacy.php`; тест групп использует общий шаблон представления.

PG-тесты разрешены **только** в отдельной БД `sitebuilder_access_test` с `SB_ACCESS_TEST_ALLOW_RESET=1`. Они удаляют тестовую схему; никогда не запускать их в `bx`.
