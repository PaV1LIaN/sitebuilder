# Управление доступом — этап 1

Новая страница: `/local/sitebuilder/access.php`. На этом этапе вход по прямому адресу. Доступны глобальные администраторы Sitebuilder из существующих настроек и администраторы Битрикса; локальные администраторы отдельных сайтов пока не получают эту общую админку. Гостевой аккаунт исключён. Проверка производится и на странице, и на каждом API-запросе.

## Работает на этом этапе

- Дерево сайтов, страниц, блоков Диска и вложенных физических папок. Папки загружаются при раскрытии, по 100 за запрос.
- Сайты: VIEWER, EDITOR (работа с файлами), ADMIN, OWNER; снятие прямого назначения с защитой последнего владельца.
- Страницы: отдельные разрешения просмотра/редактирования страницы и Диска страницы; общий существующий флаг наследования дочерними страницами. Снятие одного вида прав сохраняет другой. Это дополнительные разрешения, а НЕ явные запреты.
- В режиме `custom`: локальные правила корня Диска и папок — наследовать, запретить, читать, редактировать. Режим автоматически не переключается.
- Поиск сотрудника; вставка до 5000 строк с ФИО, ID, U123, логином или почтой. Разбор по 100 строк, однозначное точное сопоставление, ручной выбор однофамильца, исключение гостя, дедупликация по ID. Незавершённое ФИО не используется для автоматической выдачи; поиск предлагает варианты.
- Пакетное сохранение по 100 пользователей. Сохраняются только переданные сотрудники, чужие назначения не удаляются. Не более двух SQL-записей ACL на пакет; нет вызова одиночного сервиса 100 раз, создания групп или постановки заданий синхронизации.
- Версия локальной матрицы, защита повторного запроса через requestId, атомарная транзакция ACL + запись аудита. Ошибка одного пользователя отменяет весь его пакет, предыдущие успешно завершённые пакеты сохраняются. В сообщении различаются подтверждённые пакеты и неподтверждённый запрос.
- Итог вычисляется для ID сотрудника, а не для открывшего админку пользователя. Исправлены соответствующие проверки в PageAccessService, DiskPermissionService и SiteAccessRepository. Новая админка и обычный просмотр используют те же resolver-ы.

## Ограничения этапа — не считать завершением всей архитектуры

1. `bitrix_disk`: новая страница показывает итоговые возможности, но НЕ читает/не редактирует полную матрицу прямого штатного ACL. Прямые права помечены «В настройках Диска». Для записи используется существующая настройка блока. Полная массовая запись штатного ACL — следующий этап.
2. `inherit_site`: отдельные права папок здесь недоступны. Меняются роль сайта или колонка «Диск страницы» на выбранной странице. Переключение режима находится в существующих настройках блока.
3. Явный запрет страницы не добавлен; старая модель дополнения роли сайта сохранена. Новая миграция не нужна.
4. Страница показывает персональные назначения и сотрудников, найденных из роли сайта, правил страниц/папок, рабочей группы и конфигурации. Это не полный каталог всех портальных администраторов и групповых назначений. Произвольного сотрудника можно найти отдельно и увидеть его итоговые права.
5. Группы Битрикса не изменяются. Снятие прямой роли может оставить резервную роль рабочей группы. Это видно после перечитывания результата; оно не называется запретом.
6. `corp.access`, его таблицы, обработчики и задания НЕ удаляются и НЕ выключаются этим обновлением. Перед переводом рабочей выдачи прав на новую страницу остановите прежние записывающие синхронизации отдельно, иначе они смогут менять назначения. Автоматического cutover нет.
7. Блокировки локальной страницы совместимы с существующими Sitebuilder lifecycle/page-access/site-access блокировками. Старые внешние писатели, не использующие эти блокировки, не получают автоматически полной защиты от гонок.

## Выкладка

Дополнительных миграций нет. Требуются существующие таблицы `sitebuilder.access`, `sitebuilder.page_access`, `sitebuilder.disk_folder_access` и `sitebuilder.audit_log`. При их отсутствии новый endpoint выдаёт диагностическую ошибку, не создаёт схему сам.

Обновить файлы проекта; сохранить настройки `config/auth.php` и `config/auth.local.php` вашего портала. В этой разработке эти файлы не менялись. Администраторы 40, 41, 96, 97, 98, 99 и технический гость 665 в исходной сборке сохранены.

Проверка на портале: открыть новую страницу, выбрать тестовый сайт; найти отдельного сотрудника и вставить 2–3 тестовых сотрудника; назначить просмотр; проверить под обычным сотрудником. Отдельно проверить страницу без роли сайта, `custom`-папку с DENY, снятие назначения при оставшейся роли рабочей группы, защиту последнего владельца. Расширять список после этих проверок. PHP/SQL-тесты с двойниками Битрикса не заменяют проверки на вашей коробке.

## Проверки

`tests/access_admin_unit_test.php` — разбор списка, однофамильцы, дубли, валидация, совместимость прав страницы.
`tests/access_subject_identity_test.php` — чужой сотрудник не получает администратора и группы вошедшего оператора.
`tests/access_admin_pg_test.php` — настоящая PostgreSQL, массовые записи, повтор запроса, конфликт версии, атомарный откат при ошибке пользователя или аудита, сохранение соседних прав.

Последний тест допускается ТОЛЬКО на отдельной БД с точным именем `sitebuilder_access_test` и явной переменной `SB_ACCESS_TEST_ALLOW_RESET=1`: он создаёт и удаляет тестовую схему `sitebuilder`. Не запускать с реквизитами рабочего портала. Workflow `Access administration regression` запускает его на собственном контейнере PostgreSQL 16.

`tests/access_admin_browser_test.py` — офлайн-проверка интерфейса в Chromium с подменёнными ответами API: 500 сотрудников, пять пакетов, дубли, ручной выбор неоднозначного ФИО и повтор после потери ответа. Требуется Python Playwright и Chromium. Это не проверка живого Битрикса.
