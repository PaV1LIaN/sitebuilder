# Этап 13: единые миграции и preflight

## Что изменилось

Начиная с этапа 13 миграции регистрируются в PostgreSQL:

- `sitebuilder.schema_migration` — применённые SQL-файлы и их SHA-256;
- `sitebuilder.deployment_run` — история bootstrap, migrate и preflight.

Изменять уже применённый SQL-файл нельзя. Если его checksum изменился, развёртывание останавливается с `MIGRATION_CHECKSUM_DRIFT`. Исправление оформляется новым SQL-файлом.

## Первичная установка этапа 13

1. Сделать резервную копию PostgreSQL.
2. Остановить worker и изменяющие операции SiteBuilder.
3. Развернуть файлы этапа 13.
4. Открыть:

```text
/local/sitebuilder/tools/apply_stage13_migration.php
```

Страница создаст реестр, определит уже существующие этапы по структуре базы, выполнит только отсутствующие миграции и перенесёт резервные копии из `/upload/sitebuilder/backups` в приватный каталог вне `DOCUMENT_ROOT`.

## Последующие обновления

Веб-интерфейс:

```text
/local/sitebuilder/deployment.php
```

CLI:

```bash
DOCUMENT_ROOT=/home/bitrix/www \
php /home/bitrix/www/local/sitebuilder/tools/migrate_cli.php --status

DOCUMENT_ROOT=/home/bitrix/www \
php /home/bitrix/www/local/sitebuilder/tools/migrate_cli.php --apply
```

После первой установки публичных адресов откройте `deployment.php` и нажмите
`Установить публичные URL`. Действие регистрирует в штатном `urlrewrite.php`
Битрикса два правила с собственными ID `sitebuilder:public` и
`sitebuilder:sitemap`; остальные правила портала не изменяются.

Повторно нажмите эту кнопку после обновления со старой реализации ЧПУ. Установка
удалит только прежнее правило SiteBuilder, направленное в `router.php`, и запишет
новые правила с приоритетом выше общей карты сайта портала. Экран развёртывания
проверяет не только наличие правил, но и какой маршрут фактически срабатывает
первым.

Канонические адреса:

```text
/local/sitebuilder/s/{site-slug}/
/local/sitebuilder/s/{site-slug}/{parent-slug}/{page-slug}/
/local/sitebuilder/s/{site-slug}/sitemap.xml
```

Адрес `/local/sitebuilder/s/{site-slug}/` открывает домашнюю страницу без
перенаправления. В настройках сайта выберите опубликованную страницу в разделе
«Домашняя страница» и нажмите «Сохранить домашнюю страницу». Страница использует
обычные блоки, оформление и права доступа. В автоматическом режиме, а также
если выбранная страница снята с публикации, удалена или недоступна посетителю,
открывается первая доступная опубликованная страница в порядке списка.
Если таких страниц нет, возвращается 404.

Кнопка открытия сайта и ссылка домашней страницы ведут на корневой
адрес. Адреса остальных страниц, включая вложенные страницы домашней,
сохраняют полную цепочку slug. Для этого обновления миграции базы данных и
переустановка уже работающих публичных URL не требуются.

Старые ссылки `public.php?siteId=...&pageId=...` перенаправляют на канонический
адрес без ID. Переход на домашнюю страницу использует 302, поскольку её
назначение может измениться; переходы на остальные страницы используют 301.

Коды завершения CLI:

- `0` — схема актуальна;
- `1` — остались pending/drift;
- `2` — миграция завершилась ошибкой.

## Preflight

Веб-интерфейс:

```text
/local/sitebuilder/preflight.php
```

CLI:

```bash
DOCUMENT_ROOT=/home/bitrix/www \
php /home/bitrix/www/local/sitebuilder/tools/preflight_cli.php
```

Проверяются:

- версия PHP и обязательные расширения;
- `display_errors` и лимиты загрузки;
- подключение и версия PostgreSQL;
- базовые таблицы и состояние миграций;
- writable-каталоги и свободное место;
- модули `disk` и `socialnetwork`;
- технический гостевой пользователь;
- heartbeat worker, pending/dead jobs;
- открытые критические оповещения.

Коды завершения preflight CLI:

- `0` — готово к работе;
- `1` — только предупреждения;
- `2` — есть блокирующие ошибки или проверка не выполнена.

## Правило для новых миграций

1. Создать новый файл в `migrations/`.
2. Добавить его в `MigrationService::manifest()`.
3. Никогда не редактировать файл, уже зарегистрированный в production.
4. Проверить `migrate_cli.php --status` и `preflight_cli.php` до запуска worker.

## Приватное хранилище резервных копий

Новые копии сохраняются вне web-корня:

```text
dirname(DOCUMENT_ROOT)/sitebuilder-private/backups
```

Путь можно переопределить через `absolute_directory` в `config/backup.php`. Старый каталог внутри `/upload` используется только как источник одноразового переноса. Preflight блокирует production-ready статус, пока в старом каталоге остаются файлы копий.

## Ссылки на папки Диска

«Поделиться» у папки копирует ссылку на отдельную страницу SiteBuilder:
`/local/sitebuilder/components/disk/open_folder.php`. На ней доступны просмотр
содержимого и переходы по вложенным папкам. Навигация начинается с выбранной
папки; файлы открываются через существующую страницу `open_file.php`.

Ссылка не выдаёт права. При каждом открытии проверяются пользователь, связь
сайта/страницы/блока, принадлежность папки корню блока, права SiteBuilder и
штатное право чтения Битрикс.Диска. Закрытые и удалённые объекты не отображаются.
При выходе за выбранную папку или потере доступа возвращается страница с 403.
Неавторизованный получатель проходит обычный вход SiteBuilder с возвратом к ссылке.

Обновите адаптер Диска вместе с `DiskSharedFolderService.php`, `open_folder.php`
и `open_folder.css`. Миграция БД и настройка ЧПУ не нужны. Ранее скопированные
ссылки Битрикса сохраняют прежнее поведение; для новой страницы заново нажмите
«Поделиться» у папки.

Проверка без живого портала: `python3 tests/shared_folder_test.py` (PHP 8 с mbstring).

## Максимальный размер диска

В настройках блока Диска, на вкладке «Загрузка файлов», рядом с максимальным
размером файла добавлено поле «Максимальный размер диска» в МБ. Поле также
доступно в настройках блока в редакторе. Значение `0` отключает ограничение;
у существующих блоков по умолчанию установлен `0`.

Лимит хранится в `props_json.maxDiskSize` в байтах и относится к общему объёму
текущих файлов в корневой папке блока и всех её подпапках. Учитываются и файлы,
скрытые от текущего пользователя правами. Корзина и прошлые версии не входят
в этот логический объём. Если одну папку используют несколько блоков,
применяется минимальный из положительных лимитов. При записи во вложенную
папку учитываются ограничения всех её корневых папок с заданным лимитом.

Загрузка пачки файлов и копирование проверяются до записи. Перемещение
внутри того же корня не добавляет объёма; перемещение во вложенный корень
учитывает его отдельный лимит. Распаковка проверяет общий размер заранее и
повторно проверяет место перед сохранением каждого извлечённого файла.
Для подсчёта загрузки используется фактический размер временных файлов.
Проверка объёма и запись сериализуются advisory-lock PostgreSQL
`(761340, native_disk_root_id)`; при занятой блокировке API предлагает повторить
операцию, при нехватке места возвращает `DISK_QUOTA_EXCEEDED` и размеры в байтах.

Лимит можно установить ниже уже занятого объёма: существующие файлы сохраняются,
а новые данные не добавляются до освобождения места или увеличения лимита.
Ограничение действует на операции добавления через SiteBuilder. Прямые изменения
на портале Битрикса, в Office/WOPI и сторонних интеграциях не блокируются этой
настройкой; их результат учитывается при следующей проверке занятого объёма.

Миграция БД не требуется. Обновите вместе `DiskQuotaService.php`, bootstrap,
обработчики операций, нормализатор настроек и файлы интерфейса из коммита.
Проверки: `php tests/disk_quota_test.php` (PHP 8 с PDO и mbstring; БД и объекты
Битрикса заменены тестовыми адаптерами).

## Занятое место и проверка до загрузки

Под панелью команд Диска отображается общий объём активных файлов: «Занято …
из …», свободное место и полоса заполнения. При заполнении от 80% полоса
выделяется оранжевым, при отсутствии места — красным. Без лимита показывается
занятый объём без полосы. Подпапки не меняют общий объём диска; если общий
или вложенный лимит оставляет меньше места для текущей папки, это поясняется
отдельно. Подсчёт загружается отдельным запросом и не задерживает список файлов.
Ошибка подсчёта не отображается как нулевой занятый объём.

После операций и обновления списка объём пересчитывается. Другие блоки Диска
на той же странице получают уведомление об изменениях и обновляют индикатор.
Изменения из другой вкладки или напрямую в Битриксе видны после «Обновить»
и всегда заново учитываются перед следующей загрузкой.

Выбор файлов и перетаскивание используют JSON-действие `checkUpload`: передаются
только имена и размеры окончательно выбранной пачки. Сервер проверяет актуальные
лимиты диска, размер одного файла, разрешённые расширения и права пользователя.
При нехватке места показываются выбранный объём, доступный остаток и недостающий
объём; multipart-запрос не отправляется. Сбой проверки также останавливает
загрузку с предложением повторить попытку. Отказ от дубликата исключает его
из пачки. При замене перенос старого файла в историю начинается только после
успешной проверки; обычные файлы `history__*` продолжают занимать место, поэтому
новая копия учитывается целиком. Это отличается от штатных прошлых версий Битрикса.

Действия `quota` и `checkUpload` проверяют сессию, контекст страницы/блока,
принадлежность папки корню, чтение в SiteBuilder и Битриксе. `checkUpload`
дополнительно требует право загрузки. Возвращаются агрегированные размеры,
без имён закрытых файлов или данных о родительских папках других дисков.
Предварительная проверка не резервирует место: прежняя проверка фактических
байтов под блокировкой остаётся обязательной при записи.

Обновите `actions/quota.php`, `api.php`, `lib/DiskQuotaService.php`, `script.js`,
`styles.css`, `template.php` внутри `components/disk` и `views/layout/public_page.php`
вместе. Миграция БД не требуется.

Проверки без живого портала: `php tests/disk_quota_test.php`,
`python3 tests/disk_capacity_test.py`, `node tests/disk_capacity_ui_test.js`.
HTTP-проверки используют настоящие API, валидаторы и сервис прав с тестовым
хранилищем; JS-проверки используют компонент с адаптерами DOM и сети.
