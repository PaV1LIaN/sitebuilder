# Этап 9: PostgreSQL sequences и transactional outbox

## 1. Генерация ID

Основные сущности больше не получают ID через `MAX(id)+1`:

- `sitebuilder.site`;
- `sitebuilder.page`;
- `sitebuilder.block`;
- `sitebuilder.menu`.

Для них созданы канонические PostgreSQL sequences:

```text
sitebuilder.site_id_seq
sitebuilder.page_id_seq
sitebuilder.block_id_seq
sitebuilder.menu_id_seq
```

`IdSequenceService` выделяет один ID или резервирует диапазон для копирования
страницы и создания сайта из шаблона. Sequence безопасна при параллельных
транзакциях и не требует allocator-lock.

Sequence не откатывается при `ROLLBACK`. Поэтому пропуски в нумерации ID —
нормальное поведение PostgreSQL, а не потеря данных.

Миграция синхронизирует sequence с максимальным ID как в рабочей таблице, так
и в `entity_revision`. ID удалённой сущности не будет повторно выдан и не
смешает две цепочки истории.

Локальные ID внутри JSON-документов — пункты меню, блоки layout и шаблоны —
остаются локальными для своего документа. Они не являются первичными ключами
отдельных таблиц PostgreSQL.

## 2. Transactional outbox

Внешние операции больше не выполняются внутри HTTP-транзакции создания сайта
или изменения роли. В ту же транзакцию PostgreSQL записывается задание в:

```text
sitebuilder.outbox_job
sitebuilder.outbox_job_event
```

После `COMMIT` worker выполняет операцию в Битрикс24. Если HTTP-транзакция
откатилась, задание также не появится.

Очередь обрабатывает:

- создание рабочей группы сайта;
- приведение членства пользователя в группе к его прямой роли SiteBuilder;
- импорт отсутствующих ролей из рабочей группы;
- создание и привязку корневой папки сайта в Битрикс.Диске.

Обычная загрузка и удаление файлов остаются синхронными: пользователь должен
сразу получить результат файловой операции. В очередь вынесена подготовка
корневой папки сайта.

## 3. Состояния задания

```text
pending   — ожидает выполнения
running   — захвачено worker-ом
retry     — ожидает повторной попытки
succeeded — завершено успешно
cancelled — отменено администратором
dead      — исчерпаны попытки
```

Worker использует `FOR UPDATE SKIP LOCKED`, поэтому можно запустить несколько
процессов. Одно задание будет захвачено только одним процессом.

Повторные попытки используют экспоненциальную задержку. Зависшее `running`
задание автоматически возвращается в `retry` либо переводится в `dead`.

## 4. Идемпотентность и блокировки

- Создание группы и папки имеет dedupe-key: одновременно существует только
  одно активное задание данного типа для сайта.
- Задания членства читают актуальную прямую роль из PostgreSQL в момент
  выполнения. Несколько заданий приводят группу к одному итоговому состоянию.
- Операции одного пользователя в группе сериализуются advisory-lock.
- Worker получает shared `site.lifecycle`; удаление сайта получает exclusive
  lock и не пересекается с внешней операцией.
- Подготовка папки Диска использует тот же `site.disk` namespace, что загрузка
  файлов через API.

Создание группы автоматически ставит задания сверки всех прямых пользовательских
ролей сайта. Роли, назначенные до готовности группы, не потеряются.

Внешний API Битрикс24 не участвует в транзакции PostgreSQL. Если PHP-процесс
аварийно завершится ровно после создания рабочей группы, но до записи её ID в
`sitebuilder.site`, может остаться группа без привязки. Такие случаи видны по
`retry/dead` заданиям и требуют проверки администратором. Обычные исключения и
ошибки `COMMIT` компенсируются удалением только что созданной группы.

## 5. Запуск worker

### Вручную из интерфейса

```text
/local/sitebuilder/tools/run_stage9_queue.php
```

Доступно только администратору Битрикс.

### CLI

```bash
php /home/bitrix/www/local/sitebuilder/tools/queue_worker_cli.php --limit=50
```

При нестандартном document root:

```bash
DOCUMENT_ROOT=/var/www/bitrix php /var/www/bitrix/local/sitebuilder/tools/queue_worker_cli.php --limit=50
```

Пример cron раз в минуту:

```cron
* * * * * /usr/bin/php /home/bitrix/www/local/sitebuilder/tools/queue_worker_cli.php --limit=50 >> /var/log/sitebuilder-queue.log 2>&1
```

Несколько одновременных запусков допустимы.

## 6. Интерфейс заданий

```text
/local/sitebuilder/jobs.php?siteId=13
```

`OWNER` и `ADMIN` могут смотреть задания сайта, повторять завершившиеся ошибкой
и отменять ожидающие. Только администратор Битрикс может вручную запускать
worker через API.

События задания не содержат паролей, токенов и содержимого файлов. В таблице
хранятся только безопасный payload, код ошибки и сокращённый результат.

## 7. Retention

Автоматическое обслуживание удаляет:

- успешные задания старше 30 дней;
- `dead` и `cancelled` старше 90 дней.

События удаляются каскадно. Активные `pending`, `running` и `retry` не очищаются.
Сроки задаются в `config/maintenance.php`.

## 8. Установка

Этап 9 устанавливается поверх этапа 8.

1. Сделать резервную копию PostgreSQL.
2. На время обновления остановить изменяющие операции SiteBuilder: старый код с `MAX(id)+1` не должен работать параллельно с новым кодом на sequences.
3. Развернуть файлы этапа 9.
4. Применить миграцию:

```text
/local/sitebuilder/tools/apply_stage9_migration.php
```

или:

```bash
psql -d DATABASE_NAME -f migrations/20260729_004_sequences_and_external_jobs.sql
```

5. Очистить OPcache.
6. Настроить CLI worker в cron.
7. Создать тестовый сайт и проверить `jobs.php`.

До применения миграции создание новых основных сущностей завершится ошибкой,
поскольку канонические sequences ещё отсутствуют.
