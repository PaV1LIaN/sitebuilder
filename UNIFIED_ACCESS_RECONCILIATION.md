# Контроллер прав SiteBuilder, портала и Битрикс.Диска

## Назначение

`UnifiedAccessReconciliationService` выполняет одностороннюю сверку прав:

```text
sitebuilder.access + sitebuilder.page_access
    -> участники рабочей группы Битрикс24
    -> прямые пользовательские ACL корневых папок Битрикс.Диска
```

SiteBuilder является источником истины. Обратный импорт ролей из рабочей
группы не используется новым контроллером, потому что двусторонняя запись без
единого владельца приводит к циклам и непредсказуемому повышению прав.

После первого завершённого `repair` для сайта членство рабочей группы больше не
используется как резервный способ выдать роль SiteBuilder. Поэтому ручной
участник портала может оставаться в группе до решения конфликта, но сам факт
членства не откроет ему страницы SiteBuilder. До первого `repair` старый
fallback сохраняется, чтобы миграция и предварительный `audit` не вызвали
внезапную потерю доступа.

Внешние назначения контроллер всегда записывает на пользователей (`U<id>`).
Глобальные и страничные правила групп SiteBuilder (`G<id>`) разворачиваются в
активных пользователей, но не превращаются в отдельные рабочие группы портала.

## Режимы

| Режим | Поведение |
|---|---|
| `audit` | Строит план, ничего не изменяет, сохраняет результат запуска |
| `repair` | Применяет безопасные изменения, сохраняет владение правами и конфликты |

Каждый запуск выполняется через transactional outbox. Воркер берёт advisory
lock сайта, повторяет временные ошибки и применяет операции идемпотентно.
Каждое изменение прав создаёт отдельное задание: событие не потеряется, даже
если предыдущая сверка уже выполняется.

## Проекция ролей в портал

В рабочую группу попадают только глобальные роли `sitebuilder.access`, включая
эффективные роли пользователей из правил `G<id>`.
Пользователь с доступом лишь к отдельной странице не добавляется в рабочую
группу: членство группы само по себе является глобальным доступом SiteBuilder.

| Роль SiteBuilder | Роль рабочей группы |
|---|---|
| `VIEWER` | участник (`K`) |
| `EDITOR` | модератор (`E`) |
| `ADMIN` | модератор (`E`) |
| `OWNER` | модератор (`E`) |
| Фактический владелец группы | остаётся владельцем (`A`) |

Контроллер не передаёт владение рабочей группой. Группа изменяется только если
она создана SiteBuilder, имеет служебный префикс `SiteBuilder:` и в сайте
сохранён `bitrix_group_created_by`. Чужая привязанная группа доступна лишь для
аудита; расхождения становятся конфликтами.

## Проекция прав в Битрикс.Диск

Синхронизация включается только у блоков с
`permissionMode = bitrix_disk`. Для каждого пользователя, который может
открыть страницу, вычисляется эффективное право страницы.

| Эффективное право SiteBuilder | TASK Диска |
|---|---|
| глобальный `ADMIN` или `OWNER` | `disk_access_full` |
| `canDiskEdit` | `disk_access_edit` |
| `canDiskView` | `disk_access_read` |
| страница доступна, права на Диск нет | `none` — штатный отзыв доступа для пользователя |

Числовые `TASK_ID` не зафиксированы в коде. Они разрешаются через штатный
`RightsManager::getTaskIdByName()`, потому что ID могут отличаться между
инсталляциями Битрикс24.

Контроллер изменяет только прямые ACL вида `U<id>` на корневой папке. Права
групп, наследование и ACL родителей не переписываются. Администраторы Битрикс24
не получают прямые правила, поскольку их полный доступ является системным.

Для `none` контроллер через `set()` удаляет прежнее прямое положительное
правило, затем вызывает штатный `RightsManager::revokeByAccessCodes()`. Модуль
Диск сам вычисляет необходимый набор отрицательных операций с учётом
наследования папки. Существующие отрицательные правила других пользователей при
замене ACL повторно добавляются через `append()`. Контроллер принимает результат
только после строгой проверки `DiskSecurityContext::canRead() === false` и
сохраняет семантическое назначение `none` в
`sitebuilder.access_sync_binding`.

Если одна папка используется несколькими страницами, а одному пользователю
требуются разные права, контроллер не выбирает максимальное право. Он создаёт
`SHARED_FOLDER_RIGHTS_CONFLICT`; администратор должен разделить папки или
сделать требования одинаковыми.

## Владение и защита ручных изменений

Таблица `sitebuilder.access_sync_binding` хранит:

- ожидаемый уровень;
- последний уровень, применённый контроллером;
- фактический уровень на момент сверки;
- признак владения и статус;
- код конфликта и номер запуска.

Правило можно изменить автоматически, когда оно отсутствует, совпадает с
последним применённым значением или уже точно совпадает с ожидаемым и может
быть безопасно принято под управление. Незнакомое, составное либо вручную
изменённое ACL не перезаписывается.

Основные конфликты:

| Код | Значение |
|---|---|
| `UNMANAGED_EXTERNAL_RIGHT` | существует чужое право с другим уровнем |
| `EXTERNAL_RIGHT_CHANGED` | управляемое право вручную изменено после применения |
| `PORTAL_GROUP_NOT_MANAGED` | рабочая группа не принадлежит SiteBuilder |
| `BITRIX_GROUP_OWNER_PROTECTED` | операция затронула бы владельца группы |
| `SHARED_FOLDER_RIGHTS_CONFLICT` | одна папка требует разных прав на разных страницах |
| `DISK_ROOT_FOLDER_NOT_FOUND` | настроенная корневая папка удалена или недоступна |

Конфликт является штатным результатом `partial`, а не причиной бесконечного
повтора задания. Контроллер открывает одно агрегированное системное
предупреждение для сайта. `audit` также предупреждает о безопасно исправимом
drift. Предупреждение автоматически закрывается после чистой сверки или
успешного `repair`. Ошибки конкурентной версии и временные ошибки API
повторяются воркером.

## Хранение запусков

Миграция `20260827_011_unified_access_reconciliation` создаёт:

- `sitebuilder.access_reconcile_run` — результаты `audit` и `repair`;
- `sitebuilder.access_sync_binding` — реестр прав, которыми владеет контроллер.

Перед включением контроллера нужно применить Stage 22 обычным механизмом
миграций или через `tools/apply_stage22_migration.php` под администратором
Битрикс24.

## API

Все методы требуют владельца сайта.

- `site.syncAccess` — совместимый метод интерфейса; теперь ставит `repair`.
- `site.reconcileAccess: siteId, mode=audit|repair` — ставит явную сверку.
- `site.accessReconcileList: siteId, limit=25` — возвращает последние запуски.

## Автоматические триггеры

Задание `access.unified.reconcile` создаётся после:

- назначения или удаления глобальной роли SiteBuilder;
- сохранения или удаления точного права страницы;
- изменения родителя страницы, удаления страницы или копирования страницы с
  блоком Диска;
- создания, изменения, удаления или копирования блока Диска;
- сохранения настроек блока Диска;
- создания рабочей группы сайта;
- создания или повторного обнаружения корневой папки сайта.

Плановая сверка внешних ресурсов также ставит контроллер прав в том же режиме.
При стандартной конфигурации это автоматический `audit` раз в шесть часов; он
обнаруживает изменения состава групп `G<id>` и внешний drift без записи.

Сохранение матрицы ACL внутри SiteBuilder записывает подтверждённый уровень в
реестр контроллера. Прямое редактирование прав в интерфейсе самого
Битрикс24.Диска остаётся внешним изменением: следующая сверка увидит отличие от
последнего применённого уровня и зафиксирует конфликт, не отменяя решение
администратора автоматически.

## Первый запуск

1. Применить Stage 22 и убедиться, что воркер outbox работает.
2. Запустить `audit` для сайта.
3. Разобрать конфликты чужих групп, общих папок и ручных ACL.
4. Запустить `repair`.
5. Проверить результат через `site.accessReconcileList` и монитор очереди.
