# Точечные блокировки SiteBuilder — этап 8

## Назначение

До этапа 8 любой изменяющий API-запрос получал одну общую advisory-блокировку. Это было безопасно, но изменение одного сайта останавливало изменения всех остальных сайтов.

`RequestLockService` заменяет эту схему lock-планом по ресурсу. Блокировки являются transaction-level: PostgreSQL освобождает их автоматически после `COMMIT` или `ROLLBACK`.

Миграция базы данных для этапа 8 не требуется. Начиная с этапа 9 allocator-lock удалён: основные ID выдаются PostgreSQL sequences.

`site.delete` и `maintenance.run` управляют собственными транзакциями. Остальные изменяющие маршруты проходят через общий request transaction-wrapper и `RequestLockService`.

## Основные области блокировки

| Ресурс | Когда блокируется |
|---|---|
| `site.lifecycle` | shared при обычной операции сайта, exclusive при удалении, восстановлении дерева и снимке сайта |
| `site.entity` | изменение строки сайта, оформление, главная страница, привязка группы или папки Диска |
| `site.collection` | создание сайта и проверка уникальности slug |
| `page.lifecycle` | shared для обычных операций страницы, её блоков и секций; exclusive для согласованного снимка при дублировании |
| `page.tree` | создание, перемещение, копирование и изменение иерархии страниц |
| `page.entity` | изменение одной страницы без перестройки дерева |
| `page.blocks` | создание, копирование, сортировка и перемещение блоков страницы |
| `block.entity` | изменение или удаление одного блока |
| `page.sections` | изменение секций одной страницы |
| `page.access` | изменение точечных прав одной страницы |
| `menu` | изменение одного меню |
| `menu.collection` | создание меню сайта |
| `layout` | чтение с lazy-инициализацией и изменение layout сайта |
| `site.disk` | создание папки, загрузка и удаление файлов конкретного сайта |
| `template.store` | изменение общего файла шаблонов |
| `trash.item` | очистка или восстановление конкретного снимка корзины |
| `revision` | восстановление конкретной ревизии |
| `outbox.job` | ручной повтор или отмена одного задания очереди |

Числовые namespace объявлены в `lib/RequestLockService.php`. Их нельзя повторно использовать для другой семантики.

## Shared и exclusive lifecycle

Обычная операция получает:

```text
shared site.lifecycle(siteId)
```

Несколько таких операций одного сайта совместимы, если их объектные locks различаются.

Операция полного жизненного цикла получает:

```text
exclusive site.lifecycle(siteId)
```

Она ждёт завершения всех обычных операций этого сайта и не позволяет начать новые до завершения транзакции.

Exclusive lifecycle используется для:

- `site.delete`;
- `page.delete`;
- `trash.restore`;
- `template.createFromSite`.

## Примеры

### Два разных блока одной страницы

```text
Запрос A: shared site.lifecycle(13) + shared page.lifecycle(31) + block.entity(80)
Запрос B: shared site.lifecycle(13) + shared page.lifecycle(31) + block.entity(81)
```

Операции выполняются параллельно.

### Сортировка блоков одной страницы

```text
Запрос A: shared site.lifecycle(13) + shared page.lifecycle(31) + page.blocks(31)
Запрос B: shared site.lifecycle(13) + shared page.lifecycle(31) + page.blocks(31)
```

Второй запрос ждёт первый. После ожидания `expectedVersions` защищает от сохранения устаревшей сортировки.


### Дублирование страницы

```text
Обычное изменение блока: shared page.lifecycle(31)
Дублирование страницы:   exclusive page.lifecycle(31)
```

Дублирование получает согласованный снимок страницы и всех её блоков, но изменения страницы 32 того же сайта продолжают выполняться.

### Разные сайты

```text
Запрос A: shared site.lifecycle(13) + page.tree(13)
Запрос B: shared site.lifecycle(25) + page.tree(25)
```

Операции независимы.

### Удаление сайта

```text
Обычное сохранение: shared site.lifecycle(13)
Удаление:          exclusive site.lifecycle(13)
```

Удаление не пересекается с сохранением этого сайта, но не блокирует сайт 25.

## Контракт ошибок

### Ресурс занят

HTTP `423`:

```json
{
  "ok": false,
  "error": "RESOURCE_BUSY",
  "action": "block.reorder",
  "resource": "page.blocks",
  "resourceId": 31
}
```

### Deadlock или ошибка сериализации

HTTP `409`:

```json
{
  "ok": false,
  "error": "RETRY_TRANSACTION"
}
```

### Устаревшая версия

HTTP `409`:

```json
{
  "ok": false,
  "error": "VERSION_CONFLICT",
  "entityType": "block",
  "entityId": 80,
  "expectedVersion": 4,
  "currentVersion": 5
}
```

## Добавление нового API-действия

Новое изменяющее действие нельзя только добавить в роутер. Нужно:

1. добавить action в `api/index.php`;
2. добавить `case` в `RequestLockService::buildLocks()`;
3. определить минимальный набор ресурсов;
4. использовать shared lifecycle сайта для обычной операции;
5. использовать exclusive lifecycle только для действительно широкого изменения;
6. добавить action в статический тест покрытия;
7. проверить параллельный сценарий и timeout.

Если action отсутствует в lock-плане, аудит этапа 8 должен завершаться ошибкой.

## Настройка таймаута

Файл `config/locking.php`:

```php
<?php
return [
    'lock_timeout_ms' => 10000,
];
```

Слишком маленькое значение создаст ложные `RESOURCE_BUSY` при нормальных сохранениях. Слишком большое заставит HTTP-запрос долго ждать занятого объекта. Для production разумная стартовая точка — 5–10 секунд с последующей настройкой по журналу.
