# Этап 7: секции в PostgreSQL, аудит и retention

## 1. Секции страниц

Рабочее хранилище секций перенесено из:

```text
/upload/sitebuilder/page_sections.json
```

в таблицу:

```text
sitebuilder.page_section
```

JSON-файл больше не читается редактором и публичным рендером. Он используется только один раз при миграции и сохраняется как резервная копия.

Таблица хранит:

- `site_id` и `page_id`;
- заголовок и сортировку секции;
- `layout_json` и `props_json`;
- автора и даты создания/изменения;
- числовую `version`.

Создание, изменение, перемещение, восстановление и удаление секций участвуют в общей транзакции PostgreSQL. При удалении страницы её секции попадают в снимок корзины и удаляются в той же транзакции, что блоки и сама страница.

### Конфликты секций

`pageSection.update` и `pageSection.delete` требуют `expectedVersion`.

`pageSection.move` требует карту:

```json
{
  "12": 3,
  "13": 5
}
```

При устаревшей версии API возвращает `409 VERSION_CONFLICT` с `entityType = page_section`. Редактор перечитывает актуальные секции вместо молчаливой перезаписи.

## 2. Журнал действий

Таблица:

```text
sitebuilder.audit_log
```

фиксирует изменяющие API-запросы:

- пользователя Битрикс;
- действие API;
- сайт, страницу и объект;
- результат `success` или `error`;
- HTTP-статус;
- IP из `REMOTE_ADDR`;
- User-Agent;
- безопасный сокращённый набор параметров и результата;
- идентификатор запроса.

Пароли, содержимое файлов и полные данные компонентов в журнал не записываются.

Успешная запись аудита входит в одну транзакцию с изменением. Ошибки записываются после rollback. Ошибка самого аудита изолируется savepoint и не ломает основную операцию.

Интерфейс:

```text
/local/sitebuilder/audit.php?siteId=13
```

Доступ имеют администратор Битрикс и пользователи с правом управления содержимым сайта (`OWNER`/`ADMIN`). Гость `VIEWER` журнал не видит.

## 3. Срок хранения

Настройки находятся в:

```text
/local/sitebuilder/config/maintenance.php
```

Значения по умолчанию:

- ревизии — 180 дней;
- корзина — 30 дней;
- аудит — 365 дней;
- успешные задания внешних операций — 30 дней;
- ошибочные и отменённые задания — 90 дней;
- автоматический запуск — раз в сутки;
- до 5 пакетов по 2000 строк за запуск.

При очистке ревизий последняя ревизия каждой сущности сохраняется независимо от возраста.

Автоматическая очистка проверяется при обращении к API, но реально выполняется не чаще указанного интервала. Конкурентные запуски защищены advisory lock.

Ручной запуск доступен администратору Битрикс на странице журнала или через:

```text
/local/sitebuilder/tools/run_stage7_maintenance.php
```

## 4. Установка

Этап 7 устанавливается поверх этапа 6.

1. Сделать резервную копию PostgreSQL.
2. Сделать резервную копию `/upload/sitebuilder`.
3. Развернуть файлы этапа 7.
4. Открыть под администратором Битрикс:

```text
/local/sitebuilder/tools/apply_stage7_migration.php
```

5. Нажать «Применить миграцию этапа 7».
6. Убедиться, что число импортированных и пропущенных секций ожидаемое.
7. Очистить OPcache.
8. Проверить редактор и публичную страницу.

SQL-файл можно применить через `psql`, но он создаёт только таблицы. Для переноса `page_sections.json` после этого всё равно нужно один раз открыть `apply_stage7_migration.php`: повторное применение SQL безопасно, а существующие строки секций не перезаписываются.

## 5. Проверка после установки

1. Открыть страницу с несколькими секциями — порядок и оформление должны сохраниться.
2. Изменить секцию и обновить публичную страницу.
3. Открыть редактор в двух вкладках, сохранить одну секцию в первой и устаревшую версию во второй — вторая должна получить конфликт.
4. Удалить ветку страниц и восстановить её из корзины — секции и размещение блоков должны вернуться.
5. Открыть журнал и проверить последние действия.
6. Запустить retention вручную и проверить результат в блоке обслуживания.
